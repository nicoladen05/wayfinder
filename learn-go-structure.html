How Go code talks to other Go code

Your resolver is about 530 lines, all in package main. That works fine for now. This page covers how to split it into packages that each own one job, and how those packages communicate. You'll finish with four exercises that use your own functions.

First, the vocabulary

In Go, "module" and "package" have exact meanings. The part of your code that other code talks to is the package.

module

The whole project. Defined by go.mod. Yours is called wayfinder. It gives every package its import-path prefix.

package

One directory. Every .go file in that directory has the same package x line. Code in a package can see everything in it, across all its files.

file

Only there for organisation. Splitting header.go from question.go changes nothing for the compiler. Only directories draw boundaries.

A trap if you come from other languages: don't make a models package that holds all your structs, or a utils package that holds all your helpers. In Go, a type lives with the code that works on it. Header goes next to Parse and Pack, because together they are one idea: the DNS wire format.

    ├── dnsmsg/       bytes ⇄ structs

    │   ├── name.go

    ├── resolver/     asks other servers
    │   └── resolver.go
    └── server/       answers clients
        └── server.go

Why these names:

  • cmd/wayfinder holds the package main that builds the binary. It stays small: it reads config, creates the other pieces, and connects them.
  • internal/ is enforced by the compiler. Code outside the wayfinder module can't import anything under it. That means you can rename things freely without breaking anyone.
  • Your import path is the module name plus the directory: import "wayfinder/internal/dnsmsg". You then use it as dnsmsg.Parse(...).

1A capital letter is the whole API

Go has no public or private keywords. If a name starts with an uppercase letter, other packages can use it. If it starts with a lowercase letter, only its own package can. This applies to types, functions, methods, struct fields, constants and variables.

package dnsmsg

type Header struct {        // exported: resolver can use dnsmsg.Header
	ID      uint16          // exported field: resolver can set it
	QDCount uint16
}

func Parse(b []byte) (Message, error) { ... }  // exported: the "front door"
func isCompressed(label byte) bool   { ... }  // unexported: a detail nobody else needs

Your current code has three things that matter once you split it:

  • func (h DNSHeader) string() is lowercase, so fmt can't see it. Rename it to String(). Your types then satisfy fmt.Stringer, and fmt.Println(header) prints them nicely by itself.
  • dnsmsg.DNSHeader says "DNS" twice. Callers always write the package name, so call it dnsmsg.Header. The Go term for this is avoiding stutter.
  • ROOT_SERVERS starts with a capital letter, so it would be exported by accident. Go doesn't use SCREAMING_CASE. Write rootServers (private) or RootServers (public on purpose).

2Imports flow one way

If package A imports B, then B can never import A, even indirectly. The compiler rejects it with import cycle not allowed. So your packages must form layers: low-level packages at the bottom that import nothing of yours, and higher-level ones that build on them.

cmd/wayfinderknows everyone. Nobody imports it.
imports ↓
serverUDP in/out for clients. Needs a "resolver", but only as an interface.
resolverwalks root → TLD → authoritative servers
both import ↓

A good test: dnsmsg should be testable with byte slices only. No sockets, no root servers. If you catch yourself wanting net.DialUDP inside dnsmsg, the code is in the wrong layer.

3Pass shared types, and depend on small interfaces

Packages communicate through plain function calls. What they pass across the boundary is the key design choice. Two habits keep this clean:

a) Use shared types from the bottom layer

server and resolver both work with dnsmsg.Question and dnsmsg.Resource. Neither one needs to know about the other's internals. Also give dnsmsg a Message type, so callers stop tracking byte offsets like lenBytes += len:

// internal/dnsmsg/message.go
package dnsmsg

type Message struct {
	Header     Header
	Questions  []Question
	Answers    []Resource
	Authority  []Resource
	Additional []Resource
}

// Parse turns a whole UDP payload into a Message. All offset bookkeeping stays in here.
func Parse(b []byte) (Message, error) { ... }

// Pack is the inverse of Parse.
func (m Message) Pack() ([]byte, error) { ... }

b) The consumer defines the interface

The server needs something that can resolve a question. It doesn't need the concrete resolver. So the server declares a tiny interface for exactly what it uses. Go interfaces are satisfied implicitly: *resolver.Resolver never says "implements". It just has the right method.

// internal/server/server.go
package server

import "wayfinder/internal/dnsmsg"   // note: does NOT import resolver

// Resolver is what the server needs. It's defined here, where it is used.
type Resolver interface {
	Resolve(ctx context.Context, q dnsmsg.Question) ([]dnsmsg.Resource, error)
}

type Server struct {
	addr     string
	resolver Resolver
}

func New(addr string, r Resolver) *Server {
	return &Server{addr: addr, resolver: r}
}
// internal/resolver/resolver.go
package resolver

import "wayfinder/internal/dnsmsg"

type Resolver struct {
	roots []net.IP
}

func New(roots []net.IP) *Resolver { return &Resolver{roots: roots} }

// This method matches server.Resolver, so *Resolver can be passed to server.New.
func (r *Resolver) Resolve(ctx context.Context, q dnsmsg.Question) ([]dnsmsg.Resource, error) {
	...
}

c) main connects everything

// cmd/wayfinder/main.go
package main

func main() {
	r := resolver.New(resolver.RootServers)
	s := server.New("127.0.0.1:1053", r)   // config is decided here, not deep inside
	log.Fatal(s.ListenAndServe(context.Background()))
}

What you gain: to test the server, pass it a fake resolver (a struct with a Resolve method that returns fixed records), and no internet access is needed. Later you can wrap the real resolver in a cache.Resolver that has the same method, and the server doesn't change at all.
